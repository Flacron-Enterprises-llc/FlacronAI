## Project Overview

**FlacronAI** is a web platform that generates AI-assisted draft insurance inspection reports. Core loop: a user (independent adjuster, adjusting firm, inspector, agency, TPA, restoration company, etc.) enters claim/inspection details, uploads supporting documents and up to 100 photos, the "FLACRON ENGINE" (Claude-based AI service) analyzes the material and drafts a structured report, a human reviews/edits/approves it, and it's exported (PDF/DOCX/HTML) or shared.

Stack: React 18 + Vite + Tailwind (frontend), Node/Express + Firebase Firestore/Auth/Storage (backend), Anthropic Claude (primary AI, via `@anthropic-ai/sdk`) with IBM WatsonX as a text-only fallback, Stripe (billing), AWS SES (email). Full technical detail lives in `CLAUDE.md` section 4 — do not duplicate it here; refer to that file for env vars, run commands, and stack specifics.

## Major Technical Decisions & Constraints

- **Hosting:** Backend on Render (single Node web service, no persistent worker/queue infra currently provisioned); frontend on Vercel. This directly constrains Phase 7's job-queue technology choice (see Open Questions).
- **Database:** Firestore, no ORM — any new data model (per-photo records, notifications, comments, templates) must be designed as Firestore collections/subcollections consistent with existing patterns in `backend/routes/*.js`.
- **AI provider:** Claude (Anthropic) is primary; WatsonX is a text-only fallback with no vision capability — image-analysis phases (1, 7, 8) are Claude-dependent and degrade to "unavailable" without `ANTHROPIC_API_KEY`.
- **No TypeScript** anywhere in the codebase — plan changes as plain JS/JSX consistent with existing style.
- **Golden Rules in `CLAUDE.md` are non-negotiable** and apply to every phase: no fabricated claims, cautious AI language only, human review before finalize, server-side entitlement enforcement, opt-in consent for marketing, security-first for claim data, micro-changes with one task per commit, and strict `flacron/improvements`-only git workflow (no push/merge to main, no force-push).
- **Local dev environment gap:** per `CLAUDE.md`, the local backend `.env` is still missing a real `FIREBASE_API_KEY`, which blocks local testing of `/api/auth/login`, MFA login-verify, and account-deletion's password re-check. Verify this is resolved (or test against a non-local environment) before relying on local testing for phases touching those flows (notably Phase 3).

### 2026-08-18 (session 21) — Phase 16 implementation, superseded above as the "Current Active Phase" now that Phase 17 has landed; kept below for its own historical detail

**A real, serious SSRF gap was found and fixed while verifying the "preserve existing SSRF protection" instruction from the client's own task list — not a pre-planned task.** The original inline `isSafeWebhookUrl` in `backend/routes/webhooks.js` only blocked the single literal string `'127.0.0.1'` (not the other ~16.7 million addresses in `127.0.0.0/8`), had a dead IPv6 loopback check (compared against `'::1'` but Node's URL parser returns `'[::1]'` with brackets, so the comparison could never match), and had no DNS-rebinding protection at all (a wildcard-DNS hostname resolving straight to a blocked IP would sail through, since the check only ever inspected the literal hostname string).
