### [2026-08-12] — Bugfix: production login/signup/dashboard total outage — API base URL missing `/api` prefix
- **Status:** DONE, verified with build + logic checks, **UNCOMMITTED**.
- **Root cause:** Client reported live production (flacronai.com) could not log in, could not sign up, and the dashboard still showed "Account data unavailable" after the same-day auth fix (above) had already been pushed. Console showed every API call going to `https://api.flacronai.com/users/profile` etc. — **no `/api` segment at all** — with the backend correctly responding `404 Route GET /users/profile not found`. `frontend/src/services/api.js`'s API-versioning upgrade logic (added 2026-08-09, T- API versioning batch) assumed `VITE_API_URL` always already ended in `/api` or `/api/vN`; if it's configured as a bare origin (e.g. `https://api.flacronai.com`, no `/api` suffix) the `.replace(/\/api\/?$/, '/api/v1')` found no match and silently left the base with **zero** API prefix — breaking every single request (login, register, profile, everything) on any deployment where the env var is set to a bare domain. This is very likely why the previous same-day auth fix appeared not to work when the client checked live — the dashboard fix was correct, but nothing could reach the API at all in production regardless.
- **What changed:** `frontend/src/services/api.js` base-URL normalization rewritten to handle all three shapes (bare origin / `.../api` / `.../api/vN`) and always resolve to `.../api/v1`, instead of only handling two of the three and silently no-op'ing on the third. No backend or env var change required — self-healing regardless of how `VITE_API_URL` is set in Vercel.
- **Files touched:** `frontend/src/services/api.js`.
- **QA done:** Verified the exact normalization expression against all 6 realistic input shapes (bare origin with/without trailing slash, `/api` with/without trailing slash, `/api/v1`, and the `localhost:3000/api` local default) in isolation — all resolve to the correct `.../api/v1`. Frontend lint 0 errors, tests 4/4 pass, production build passes (including a build performed with `VITE_API_URL` set to the exact bare-origin shape that broke production, to confirm the build succeeds and embeds the value for the corrected runtime logic to process).
- **Left / follow-ups:** Could not verify directly against the live Vercel deployment (no deploy access from this session) — this fix makes the frontend self-healing regardless of the actual `VITE_API_URL` value, but it is still worth the client checking/fixing the Vercel env var to the canonical `https://api.flacronai.com/api` (or `/api/v1`) form for clarity, since a bare origin was almost certainly what was configured. ### [2026-08-12] — Bugfix: intermittent "Account data unavailable" on dashboard
- **Status:** DONE — live-QA'd with real browser automation (Playwright), **UNCOMMITTED**.
- **Root cause (two distinct contributing bugs, not one):**
  1. **No auto-recovery from a transient profile-fetch failure.** `AuthContext.jsx`'s `fetchUserProfile` retried a failed `/users/profile` call up to 2 times over ~1.8s, then permanently set `profileError` with nothing to ever retry it again — the user was stuck on the "Account data unavailable" screen until they manually clicked "Retry loading," even though the underlying blip (a slow/cold Firestore connection, a dropped request, a momentary token-refresh race) had often already cleared itself a few seconds later.
  2. **Backend conflated "token verification failed" with "a valid token's data lookup failed."** `middleware/auth.js`'s `authenticateToken` ran the Firestore profile lookup inside the *same* try/catch as Firebase ID-token verification. If `verifyIdToken` succeeded but the following Firestore read threw (any transient DB hiccup), execution fell into the JWT-fallback branch, which also failed (it wasn't a JWT), producing `401 INVALID_TOKEN` for a **genuinely valid** token — an unrecoverable-looking error for what was actually a retryable infrastructure blip.
  - Reproduced live during QA: an already-running local backend instance (started before this session, healthy per `/health`) rejected every freshly-issued, valid Firebase ID token with `401 INVALID_TOKEN` — confirmed via a standalone Admin SDK script that verified the *same* token successfully. Restarting the backend process resolved it immediately, matching the exact failure mode already documented in the 2026-08-02 "Local account-data authentication restored" entry above. This class of failure (a long-running Node process getting into a bad state where cert/token verification silently starts failing) is an infra/process-health issue, not something fixable from application code — but it is now handled much better on both ends.
- **What changed:**
  - `backend/middleware/auth.js`: split `authenticateToken` so a Firestore lookup failure *after* a successful token verification returns `503 PROFILE_LOOKUP_FAILED` instead of `401 INVALID_TOKEN`, so the client can tell "retry me" apart from "log in again."
  - `frontend/src/services/api.js`: the response interceptor now retries once on a `503` or a plain network error (no response received) with a 1s delay, the same pattern already used for `429`. Timeouts (`ECONNABORTED`) are excluded so slow AI-generation requests aren't doubled.
